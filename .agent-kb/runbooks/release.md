# Release Runbook — sbom-validator

> Read by the release-manager at G8; publication only after human GO at H3.

## Artifacts
- Python package: `poetry build` → `dist/*.whl` and `dist/*.tar.gz`; CLI command `sbom-validator`.
- Standalone binaries (Linux amd64, Windows amd64) built by `.github/workflows/release.yml` with PyInstaller (`sbom_validator.spec`), plus `.sha256` checksums.
- The project's own SBOMs (CycloneDX 1.6 JSON + SPDX 2.3 JSON) with checksums, generated by `release.yml` (`sbom-dry-run.yml` is a manual dry run).
- All attached to the GitHub Release for the tag.

## Branch Flow
- Release prep runs on the feature branch (`release_flow: same-branch`): G8, G9, G10 and closeout are committed there, and the PR to `develop` carries the release evidence.
- `develop` → `master` via PR for stable releases.
- The tag commit must be on `master` or `develop` (enforced by the `verify-tag-provenance` job).

## Release Gates (project-specific, in addition to the generic release-manager gates)
1. **Version consistency:** `pyproject.toml` == `src/sbom_validator/__init__.py`; the CHANGELOG section exists.
2. **Packaging:** `poetry build` succeeds; `.whl` and `.tar.gz` exist in `dist/`.
3. **CLI compatibility:** `sbom-validator --help` and `sbom-validator validate --help` work; exit codes 0/1/2 are unchanged; JSON keys `status`, `file`, `format_detected`, `issues` are unchanged.
4. **Binary smoke test:** see below.
5. **Release workflow:** tag trigger `v*.*.*`; schemas bundled via `datas` in `sbom_validator.spec`; the smoke step calls `scripts/smoke-test-binary.sh`, not a bare `--version`.
6. **CI-enforced analytics:** `release.yml` fails if `docs/releases/token-report-vX.Y.Z.html` or `docs/releases/workflow-report-vX.Y.Z.html` is missing for the tag. G9/G10 must be committed before tagging.

## Smoke Test
- Build locally: `bash scripts/build_binary.sh` (runs `poetry run pyinstaller sbom_validator.spec`).
- Run: `bash scripts/smoke-test-binary.sh ./dist/sbom-validator` (Linux) or `./dist/sbom-validator.exe` (Windows).
- It must verify `--version` output, `--help` output, PASS/FAIL/ERROR exit codes on real fixtures in `tests/fixtures`, and `--report-dir` file generation. An exit-code-only check is insufficient.
- If a local binary build is impossible, confirm that the release workflow smoke step is green.

## Publication (only after H3 GO)
1. Make sure the release commit is on `develop` or `master`.
2. `git tag vX.Y.Z && git push origin vX.Y.Z` — this triggers `release.yml` (provenance, report checks, SBOMs, Linux and Windows binaries).
3. Verify the GitHub Release has the binaries, checksums and SBOMs.
4. Record the tag and date in the tracker's Final Verdict.

## Post-Release
- Delete merged feature branches (remote is auto-deleted; delete locally).
- Move any open deferrals to the next release tracker / `TASKS.md`.
